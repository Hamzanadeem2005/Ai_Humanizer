# Requirements — HumanizeAI

> All requirements in this document are derived exclusively from reading the actual source code and
> configuration files in this repository. Nothing is assumed or invented.

---

## Product Overview

HumanizeAI is a web application that takes AI-generated text as input and rewrites it so it reads
more naturally, with varied sentence rhythm and everyday vocabulary. It is a text rewriting and
style-adaptation tool. It does **not** guarantee undetectability by any external service or
authorship by a human.

---

## Problem Statement

Text generated by AI tools tends to share recognisable stylistic patterns: uniform sentence length,
formal transitional phrases ("furthermore", "in conclusion"), low use of contractions, and
repetitive vocabulary. HumanizeAI rewrites such text using rule-based transformations and optionally
an AI-powered rewrite to make it read more like something a person wrote casually.

---

## Target Users

- Students who want to rephrase AI-drafted study notes into their own voice
- Professionals adapting AI-drafted content to a particular writing style
- Writers using AI tools as a starting point and wanting a more natural output

---

## Core User Journey (Verified)

1. User visits the app, sees the landing page, and creates a free account (name, email, password)
2. User logs in and lands on the Dashboard
3. User pastes AI-generated text (up to 5,000 characters) into the input panel
4. User selects a mode (Basic or Advanced), a tone, and optionally a length preference
5. User clicks "Humanize" and waits for the rewritten result
6. User copies the output or downloads it as a `.txt` file
7. The run is automatically saved to History
8. User can review past runs on the History page and delete individual entries
9. User can view personal usage statistics on the Analytics page
10. User can leave a 1–5 star rating and comment on any history entry

## Functional Requirements

### Authentication

**REQ-001** — Registration  
The system shall allow a new user to register with a full name, email address, and password.  
- Name: required, minimum 2 characters (validated client-side)  
- Email: required, must match a valid email format, must be unique across all accounts  
- Password: required, minimum 6 characters (validated client-side)  
- Password confirmation must match password (validated client-side)  
*Acceptance:* A new row is created in `users`. The system returns HTTP 200 with a success message.  
*Acceptance:* Duplicate email returns HTTP 409 with a clear error message.

**REQ-002** — Login  
The system shall authenticate a user by email and password.  
- Both fields are required  
- On success: returns `userId`, `username`, `sessionId`, and `token` (`session-{id}`)  
- Login is recorded in `usersessions` with IP address and login timestamp  
*Acceptance:* Correct credentials return HTTP 200 with user data.  
*Acceptance:* Incorrect credentials return HTTP 401 with a human-readable message.

**REQ-003** — Session Persistence  
The system shall store the authenticated user object in `localStorage` (`hai_user`) so the session
survives a page refresh.

**REQ-004** — Route Protection  
All authenticated pages (Dashboard, History, Analytics, Settings) shall redirect to `login.html`
if no valid user object exists in `localStorage`.

**REQ-005** — Logout  
The system shall clear the `localStorage` user object and redirect to `login.html` on logout.

**REQ-006** — Session Management  
The system shall allow a user to revoke all login sessions except the most recently active one via
the `/api/auth/sessions/{userId}/revoke-others` endpoint.

### Text Humanization — Input

**REQ-010** — Text Input  
The dashboard shall provide a `<textarea>` accepting up to 5,000 characters of input text.

**REQ-011** — Empty Input Guard  
Submitting an empty or whitespace-only input shall display an inline message and not call the API.

**REQ-012** — Character / Word Counter  
The UI shall display a live word count and character count (`N words · M / 5000`) as the user types.

**REQ-013** — Draft Persistence  
The input text shall be auto-saved to `localStorage` (key: `hai_draft_{userId}`) and restored when
the user returns to the dashboard.

**REQ-014** — Clear Button  
A "Clear" button shall wipe the input, the output panel, and the saved draft from `localStorage`.

**REQ-015** — Example Text  
A "Try an example" button shall pre-fill the input with a sample AI-generated paragraph.

**REQ-016** — Keyboard Shortcut  
`Ctrl+Enter` (or `Cmd+Enter` on macOS) shall trigger the humanize/detect action.

---

### Text Humanization — Mode Selection

**REQ-020** — Mode Toggle  
The UI shall display three mode buttons: Basic, Advanced, AI Detector. Exactly one is active
(`aria-pressed="true"`) at a time.

**REQ-021** — Default Mode Preference  
The last-used mode preference (`hai_pref_mode`) shall be stored in `localStorage` and applied on
next dashboard load.

---

### Text Humanization — Basic Mode

**REQ-030** — Offline Processing  
Basic mode shall rewrite text entirely offline using:  
1. A hardcoded dictionary of AI stock phrases mapped to simpler alternatives  
2. Word-for-word synonym substitution from the `humanizationdictionary` database table  
3. Contraction conversion (`do not` → `don't`, `it is` → `it's`, etc.)  
4. A final polish pass removing additional AI-tell phrases and normalising whitespace/punctuation

**REQ-031** — Basic Mode Response  
The response shall include: `humanizedText`, `aiScore`, `humanScore`, `mode` (`"basic"`), `message`.

**REQ-032** — History Recording  
Every Basic mode run shall be saved to the `transformationhistory` table with the tone ID.

---

### Text Humanization — Advanced Mode

**REQ-040** — AI-Powered Rewrite  
Advanced mode shall send the input text to the OpenRouter API (`openai/gpt-4o-mini`) with a
system prompt that instructs the model to produce human-sounding prose with: varied sentence
rhythm, contractions, no AI-tell phrases, correct tone, and length as requested.

**REQ-041** — Tone Application  
The selected tone (Casual / Formal / Academic / Professional) shall be included in the AI prompt
to shape the rewrite style.

**REQ-042** — Length Control  
The selected length option (Same / Shorter / Longer) shall be passed to the AI prompt as an
explicit instruction.

**REQ-043** — Timeout  
The API call shall time out after 30 seconds.

**REQ-044** — Offline Fallback  
If the AI API call fails for any reason (network error, invalid key, timeout, error response), the
system shall fall back to the offline `AdvancedHumanizer` (which extends `BasicHumanizer` with
additional conversational phrase substitutions) and continue without surfacing the error to the
user as a failure.

**REQ-045** — Advanced Mode Response  
The response format is identical to Basic mode (REQ-031), with `mode` set to `"advanced"`.

---

### AI Detector Mode

**REQ-050** — Score Without Rewriting  
In Detect mode, submitting text shall call `/api/humanize/detect` and return `aiScore`, `humanScore`,
and a plain-English `verdict` without modifying the input text.

**REQ-051** — Verdict Values  
The verdict shall be one of:  
- `"Likely AI-generated"` — aiScore ≥ 60  
- `"Possibly AI-assisted"` — aiScore 30–59  
- `"Likely human"` — aiScore < 30

**REQ-052** — AI Pattern Highlighting  
The frontend shall highlight detected AI-marker phrases within the analysed text using a styled
`<mark>` element, and display a count of matched patterns.

**REQ-053** — Score Meter  
The output panel shall show an animated progress bar displaying the AI score percentage.

---

### Scoring Engine

**REQ-060** — AI Score Calculation  
The `ScoreCalculator.CalculateAIScore()` method shall produce a 0–100 integer based on:  
- Presence of AI-tell phrases (each +14 points)  
- Presence of AI-tell single words (each +6 points)  
- Low contraction density in texts > 25 words (+14 if zero contractions)  
- High density of long words (≥ 9 chars) (+6–12 points)  
- Low sentence-length variance (+6–12 if sentences are too uniform)  
- Presence of casual/human words (each −8 points)  
- High contraction density (−18 points)  
- Presence of formal punctuation (semicolons, em/en dashes, +4 each, capped at +12)  
- Result clamped to [0, 100]

**REQ-061** — Human Score  
`humanScore` = `100 − aiScore`, always.

---

### History

**REQ-070** — History Retrieval  
The History page shall load and display the last 50 humanization runs for the logged-in user,
ordered newest-first, including: input snippet, output snippet, AI/Human scores, tone name,
timestamp.

**REQ-071** — History Search  
A search input shall filter displayed history entries client-side by matching against the entry
title, input text, and output text (case-insensitive substring match).

**REQ-072** — Copy Output  
Each history entry shall have a "Copy" button that writes the full `outputText` to the clipboard.

**REQ-073** — Delete Entry  
Each history entry shall have a "Delete" button that calls `DELETE /api/humanize/history/{id}`,
removes the entry (and any associated feedback) from the database, and removes it from the
displayed list without a page reload.

---

### Analytics

**REQ-080** — Summary Statistics  
The Analytics page shall display: total runs, total words humanized, average AI-score reduction.

**REQ-081** — Usage Chart  
A Canvas-based bar chart shall show the number of humanization runs per day for the last 7 days.

**REQ-082** — Mode Breakdown  
Progress bars shall show the percentage of Basic vs Advanced mode runs based on client-side
`localStorage` counters.

**REQ-083** — Detailed Table  
The last 10 runs shall appear in a table showing: date, tone, words in, words out, AI reduction.

---

### Feedback

**REQ-090** — Submit Feedback  
The system shall accept a 1–5 star rating and optional text comment linked to a history entry ID
via `POST /api/feedback`.

**REQ-091** — Retrieve Feedback  
The system shall return all feedback submitted by a user via `GET /api/feedback/{userId}`.

---

### Output Actions

**REQ-100** — Copy Output  
A "Copy" button on the dashboard output panel shall write the humanized text to the clipboard
and show a toast notification confirming the action.

**REQ-101** — Download Output  
A "Save" button shall trigger a browser download of the humanized text as `humanized.txt`.

## Non-Functional Requirements

### Performance

**REQ-110** — Basic Mode Response Time  
Basic mode shall complete and return a response within 2 seconds under normal local conditions
(no external API call).

**REQ-111** — Advanced Mode Timeout  
Advanced mode shall not block the UI for more than 30 seconds; the API call is capped at 30 s and
a fallback is triggered on failure.

**REQ-112** — Loading Feedback  
The UI shall display a skeleton loading animation and a disabled submit button during any pending
API call.

---

### Responsiveness

**REQ-120** — Mobile Navigation  
The navigation bar shall collapse to a hamburger toggle below 860 px viewport width.

**REQ-121** — History Table  
The analytics detail table shall be horizontally scrollable below 640 px viewport width.

---

### Accessibility

**REQ-130** — ARIA Labels  
All interactive regions, form controls, buttons, and live output areas shall carry appropriate
`aria-label`, `aria-live`, `role`, and `aria-pressed` attributes as implemented.

**REQ-131** — Focus Management  
All interactive elements shall be keyboard-navigable and display a visible focus ring using
`focus-visible` styling.

**REQ-132** — Status Announcements  
Alert messages and output results shall use `aria-live="polite"` so screen readers announce them.

---

### Privacy

**REQ-140** — User Text  
All text submitted for humanization is transmitted to the backend over the local network only
(localhost by default). In Advanced mode, text is forwarded to the OpenRouter API. Users should
be aware of this when processing sensitive content.

**REQ-141** — Session Storage  
User session data (user ID, display name, email, token) is stored in `localStorage`.
No sensitive data beyond the session token is persisted in the browser.

---

### Security (Current State — Issues Noted)

**REQ-150** — API Key Storage *(Not Yet Compliant)*  
The OpenRouter API key shall be stored in an environment variable or secrets manager, not in source
code. **Currently hardcoded — must be fixed before production deployment or public repository push.**

**REQ-151** — Database Credentials *(Not Yet Compliant)*  
The MySQL connection string shall be stored in environment configuration (`appsettings.json` or
environment variables), not hardcoded in `DatabaseService.cs`.
**Currently hardcoded — must be fixed before repository push.**

**REQ-152** — Password Storage *(Not Yet Compliant)*  
Passwords shall be hashed with a modern algorithm (e.g., BCrypt) before storage.
**Currently stored in plaintext — must be fixed before any real user data is collected.**

**REQ-153** — CORS Policy  
The current `AllowAnyOrigin` CORS policy is acceptable for local development but shall be
restricted to known origins before any internet-facing deployment.
